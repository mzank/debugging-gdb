# CUDA-GDB Cheat Sheet

CUDA-GDB is NVIDIA's debugger for CUDA host (CPU) and device (GPU) code. It is
based on GNU GDB, so standard GDB commands work unchanged. This cheat sheet
covers the CUDA/GPU-specific commands and behavior; common host-debugging
commands are documented in
[`gdb/gdb_cheat_sheet.md`](../gdb/gdb_cheat_sheet.md). See the
[NVIDIA CUDA-GDB documentation](https://docs.nvidia.com/cuda/cuda-gdb/) for
the complete command reference.

Commands use `program` as the program name. Source file names and paths are
illustrative; adapt them to your project.

## 1. Command reference

The commands below are CUDA-specific and are not covered in the GDB cheat
sheet.

| Command | Description |
| --- | --- |
| **Starting CUDA-GDB** | |
| `cuda-gdb <program>` | Start CUDA-GDB with a program |
| `cuda-gdb -x <command-file> <program>` | Start CUDA-GDB and execute the commands in a command file |
| **CUDA focus** | |
| `cuda device [N]` | Display the current CUDA device, or select device N |
| `cuda block <N>` | Select CUDA block N in the current kernel |
| `cuda thread <N>` | Select CUDA thread N in the current block |
| `cuda block <N> thread <M>` | Select thread M in block N |
| `cuda sm <N>` | Select streaming multiprocessor (SM) N |
| `cuda warp <N>` | Select warp N in the current SM |
| `cuda lane <N>` | Select lane N in the current warp |
| `cuda warp <N> lane <M>` | Select lane M in warp N of the current SM |
| `cuda sm <N> warp <M> lane <L>` | Select lane L in warp M of SM N |
| **Inspecting CUDA execution** | |
| `info cuda devices` | List CUDA devices visible to the debugger |
| `info cuda kernels` | List active CUDA kernels |
| `info cuda sms` | List SMs and their active warps |
| `info cuda warps` | List warps in the current SM |
| `info cuda lanes` | List lanes in the current warp |
| `info cuda blocks` | List blocks in the current kernel |
| `info cuda threads` | List CUDA threads in the current kernel |
| **CUDA built-in variables** | |
| `print threadIdx` | Display the current CUDA thread index; use `.x`, `.y`, `.z` for a component |
| `print blockIdx` | Display the current CUDA block index; use `.x`, `.y`, `.z` for a component |
| `print blockDim` | Display the CUDA block dimensions |
| `print gridDim` | Display the CUDA grid dimensions |

## 2. Compile with CUDA debugging information

Use `nvcc` for CUDA kernels and `.cu` files:

```bash
nvcc -g -G -O0 program.cu -o program
```

Use `nvc++` for C++ (`.cpp`) files with GPU offloading via OpenACC or OpenMP:

```bash
nvc++ -g -O0 -acc -gpu=debug -Minfo=accel program.cpp -o program

nvc++ -g -O0 -mp=gpu -gpu=debug -Minfo=mp program.cpp -o program
```

Use `nvc` for C (`.c`) files with GPU offloading via OpenACC or OpenMP:

```bash
nvc -g -O0 -acc -gpu=debug -Minfo=accel program.c -o program

nvc -g -O0 -mp=gpu -gpu=debug -Minfo=mp program.c -o program
```

Choose the command that matches your source file; each command produces an
executable named `program`.

Explanation:

- `-g`: Debugging symbols for host (CPU) code.
- `-G`: Debugging information for CUDA device (GPU) code (`nvcc` only).
- `-gpu=debug`: Debugging information for GPU code generated by `nvc` and
  `nvc++`.
- `-acc`: Enable OpenACC.
- `-mp=gpu`: Enable OpenMP GPU offloading.
- `-O0`: Disable compiler optimizations.
- `-Minfo=accel` / `-Minfo=mp`: Print OpenACC/OpenMP offload information.

For CUDA code, `-g` and `-G` are needed to debug host and device code in the
same session. For OpenACC and OpenMP code, `-g` and `-gpu=debug` provide host and
device debugging symbols. Optimized device code can prevent CUDA-GDB from
stopping at the expected source lines.

## 3. Start CUDA-GDB

Start CUDA-GDB with the compiled program:

```bash
cuda-gdb ./program
```

You should see the CUDA-GDB prompt:

```text
(cuda-gdb)
```

To run a command file at startup:

```bash
cuda-gdb -x commands.txt ./program
```

The same command works for CUDA, OpenACC, and OpenMP builds.

Command files are useful for reproducible debugging sessions. They may also
contain standard GDB commands, which are documented in the GDB cheat sheet.
Most standard GDB startup options also work; see the GDB cheat sheet for
details.

## 4. CUDA focus and execution inspection

When a breakpoint in a CUDA kernel is hit, CUDA-GDB switches focus to a CUDA
thread and reports the kernel, grid, block, thread, device, SM, warp, and lane:

```text
(cuda-gdb) break kernel
(cuda-gdb) run
...
[Switching focus to CUDA kernel 0, grid 1, block (0,0,0), thread (0,0,0), device 0, sm 0, warp 0, lane 0]
CUDA thread hit Breakpoint 1, kernel<<<(15,1,1),(67,1,1)>>> (...) at program.cu:35
```

Standard GDB commands such as `break`, `run`, `next`, and `continue` are
documented in the GDB cheat sheet. CUDA focus commands require an active CUDA
context; the `info cuda` commands list only the devices, kernels, blocks,
threads, warps, and lanes relevant to the current session and focus.

### 4.1 List devices, kernels, and GPU resources

```text
(cuda-gdb) info cuda devices
(cuda-gdb) info cuda kernels
(cuda-gdb) info cuda sms
(cuda-gdb) info cuda blocks
(cuda-gdb) info cuda threads
```

`info cuda blocks` and `info cuda threads` show ranges of CUDA blocks and
threads, while `info cuda sms` shows which SMs have active warps in the current
focus.

### 4.2 Select a CUDA focus

Select a specific block and thread:

```text
(cuda-gdb) cuda block 3 thread 35
```

Example output:

```text
[Switching focus to CUDA kernel 0, grid 1, block (3,0,0), thread (35,0,0), device 0, sm 6, warp 1, lane 3]
```

The same CUDA thread can also be selected by SM, warp, and lane:

```text
(cuda-gdb) cuda sm 6 warp 1 lane 3
```

or by warp and lane within the current SM:

```text
(cuda-gdb) cuda warp 1 lane 3
```

Use `info cuda warps` and `info cuda lanes` to list the valid coordinates in the
current focus before selecting a warp or lane. See
[Software and hardware views](#5-software-and-hardware-views) for the
distinction between the software and hardware coordinates.

### 4.3 Inspect CUDA built-in variables

Once a CUDA thread is focused, inspect its execution coordinates and device
variables:

```text
(cuda-gdb) print threadIdx
$1 = {x = 35, y = 0, z = 0}
(cuda-gdb) print blockIdx
$2 = {x = 3, y = 0, z = 0}
(cuda-gdb) print blockDim
$3 = {x = 67, y = 1, z = 1}
(cuda-gdb) print gridDim
$4 = {x = 15, y = 1, z = 1}
(cuda-gdb) print value
$5 = 236
```

The exact coordinates depend on the kernel launch configuration and the focused
thread. Use `print threadIdx.x`, `print blockIdx.x`, and so on to inspect a
single component.

## 5. Software and hardware views

CUDA execution can be described from two views:

- **Software view:** the program launches a grid of blocks, and each block
  contains threads. CUDA exposes the block and thread coordinates and
  dimensions through `blockIdx`, `blockDim`, `gridDim`, and `threadIdx`.
  OpenACC and OpenMP expose hierarchical parallelism through concepts such as
  gangs, workers, vectors, teams, and threads. NVIDIA GPU implementations can
  map these concepts onto CUDA blocks and threads, which CUDA-GDB can then
  expose through its CUDA execution coordinates.
- **Hardware view:** the GPU executes warps, and each warp contains lanes. A
  CUDA thread runs on a lane. CUDA-GDB single-steps at warp granularity, which
  advances all active threads in the focused warp; divergent threads in that
  warp are not advanced.

NVIDIA GPUs use the Single Instruction, Multiple Threads (SIMT) execution
model. Threads are grouped into warps and execute instructions together, with
individual lanes potentially becoming inactive because of divergence or other
execution conditions. The hardware hierarchy is:

- **Device:** the GPU that contains the SMs.
- **Streaming Multiprocessor (SM):** the hardware unit that schedules and
  executes warps.
- **SM sub-partition:** an execution partition within an SM. On the NVIDIA RTX
  A5000 (`sm_86`), each SM has four sub-partitions, each with a warp scheduler
  and 32 CUDA cores. These provide 128 FP32 CUDA cores per SM. Other
  instruction types use their corresponding execution resources.
- **Warp:** a group of 32 lanes; this is NVIDIA's warp size, reported by
  CUDA-GDB as `Lanes/Warp`.
- **Lane:** an individual execution position within a warp. A lane occupied by
  a thread maps to exactly one CUDA thread. A thread that diverges still
  occupies its lane but is not active, while the unoccupied lanes at the end of
  a partially populated warp map to no thread at all.

A few important details:

- A block is assigned to a single SM, and its warps execute on that SM.
- Multiple warps from the same or different blocks can reside on the same SM.
- An SM can keep multiple warps resident and issue instructions from several
  warps concurrently. Residency is limited by resources such as registers and
  shared memory; the four sub-partitions each have a warp scheduler.
- FP32 CUDA cores are physical arithmetic units. A GPU has far fewer FP32
  cores than the CUDA threads it can keep resident.

### 5.1 CUDA-GDB hardware information

In CUDA-GDB, `info cuda devices` reports the hardware resources of each GPU
through the `SMs`, `Warps/SM`, `Lanes/Warp`, and `Max Regs/Lane` columns.

For the captured system, device 0 reports (the run has four GPUs; the other
rows are omitted):

```text
  Dev PCI Bus/Dev ID             Name Description SM Type SMs Warps/SM Lanes/Warp Max Regs/Lane ...
*   0        21:00.0 NVIDIA RTX A5000   GA102GL-A   sm_86  64       48         32           255 ...
```

In this output:

- **`*`:** marks the device that currently has CUDA-GDB's focus.
- **Dev:** CUDA device number, used by `cuda device N`.
- **SMs:** number of streaming multiprocessors (64).
- **Warps/SM:** maximum number of warps that can reside on one SM (48).
- **Lanes/Warp:** number of lanes in a warp, i.e. the warp size (32).
- **Max Regs/Lane:** maximum number of 32-bit registers that can be allocated
  per thread (255), an architectural limit for `sm_86`. An SM has 65,536 32-bit
  registers in total, so a kernel using 255 registers per thread fits only a
  small number of warps regardless of the `Warps/SM` maximum.

The relationship between these values and the hardware capacity is:

- 64 Streaming Multiprocessors.
- 128 FP32 CUDA cores per SM (32 in each of the four sub-partitions).
- 8,192 FP32 CUDA cores in total. CUDA-GDB does not report the core count; it
  is architecture data for `sm_86`.
- 48 warps can be resident per SM (1,536 CUDA threads).
- 3,072 warps can be resident in total.
- 32 lanes per warp.
- 98,304 CUDA threads can be resident in total.

Thus:

```text
FP32 CUDA cores      = 64 SMs * 128 cores/SM           = 8,192
Max resident warps   = 64 SMs * 48 warps/SM            = 3,072
Max resident threads = 64 SMs * 48 warps/SM * 32 lanes = 98,304
```

These are theoretical maxima. The actual number of resident warps is limited by
the resources each kernel needs, principally registers and shared memory. For
example, on `sm_86` registers are allocated per warp in units of 256 registers
(8 per thread), so 255 registers per thread rounds up to 256 per thread and
8,192 per warp. An SM with 65,536 registers can therefore hold only eight such
warps (256 threads), well below the 48-warp maximum.

**FP32 vs. FP64:** NVIDIA's "CUDA core" count refers to FP32 execution units,
so the 128 per SM and 8,192 total above describe FP32 capacity. FP64 operations
use separate FP64 units, which are much less numerous. On the GA102 chip in the
RTX A5000, each SM has two FP64 units (128 in total), giving roughly 1/64 of
the FP32 throughput. These units are not included in the CUDA-core count and
are not reported by `info cuda devices`. Data-center GPUs such as the A100
provide substantially more FP64 capacity.

A kernel launch is described by its grid and block dimensions. The number of
CUDA threads in the launch is the product of all grid and block dimensions:

```text
CUDA threads per block  = blockDim.x * blockDim.y * blockDim.z
CUDA threads per launch = gridDim.x * gridDim.y * gridDim.z
                          * blockDim.x * blockDim.y * blockDim.z
```

For the launches captured in this repository:

- `vectorAdd<<<(15,1,1),(67,1,1)>>>`: 15 * 67 = 1,005 CUDA threads.
- `vectorAddStride<<<(5,1,1),(71,1,1)>>>`: 5 * 71 = 355 CUDA threads.
- The OpenACC and OpenMP kernels each use `<<<(8,1,1),(128,1,1)>>>`: 8 * 128 =
  1,024 CUDA threads.

The warps needed per block are `ceil(CUDA threads per block / Lanes per warp)`.
The 67-thread block uses three warps: two full warps and one partial warp
containing 3 threads. The 71-thread block also uses three warps, the last with
7 threads. The 128-thread block uses four warps of 32 threads each.

**Important distinction:** The 98,304 figure is the maximum number of CUDA
threads that can be resident on the GPU, not the number of threads launched by
a kernel and not the number executing instructions at one instant. A launch can
create more threads than can be resident; they execute in successive waves as
warps are scheduled. Likewise, `Lanes/Warp` is the warp size, not a block size.

### 5.2 Mapping between software and hardware views

The mapping between the two views is not one-to-one. A block is decomposed
into one or more warps, and a warp is not necessarily fully used.

For example, on the captured NVIDIA RTX A5000 (`sm_86`) system, a warp has 32
lanes, but a block with 67 threads occupies three warps: two full warps and one
partial warp containing 3 threads. `info cuda warps` shows which lanes of each
warp are active, while `info cuda lanes` lists only the lanes that map to
threads, so the partial warp shows three lanes. Divergence is not the same as an
unoccupied lane: a divergent thread still maps to a lane, whereas the unused
lanes at the end of a partial warp do not.

CUDA-GDB reports the software view through `info cuda blocks`,
`info cuda threads`, and the `blockIdx`/`threadIdx` variables, and the hardware
view through `info cuda sms`, `info cuda warps`, and `info cuda lanes`. The same
CUDA thread can be selected by either view: `cuda block 3 thread 35` selects the
thread by software coordinates, while `cuda sm 6 warp 1 lane 3` selects it by
hardware coordinates.

The lane coordinate can be derived from the thread's position in its block:
for a block of `blockDim.x` by `blockDim.y` by `blockDim.z` threads, the linear
thread index is `threadIdx.x + blockDim.x * (threadIdx.y + blockDim.y *
threadIdx.z)`, the block-relative warp is `linear_tid / 32` (integer division),
and the lane is `linear_tid % 32`. The SM and hardware warp slot are
placement-dependent and must be obtained from CUDA-GDB. In the captured
`vectorAddStride` launch, block 4 has 71 threads: thread 31 is block-relative
warp 0, lane 31, but CUDA-GDB reports it as `sm 8, warp 3, lane 31`; thread 65
is block-relative warp 2, lane 1, but CUDA-GDB reports it as `sm 8, warp 1,
lane 1`. The block-relative and hardware warp numbers therefore differ, while
the lane number does not.

## 6. CUDA debugging notes

- Host and device debugging are separate. Use the standard GDB `thread` and
  `frame` commands for host threads, and the `cuda` commands for GPU focus.
- GPU single-stepping operates at warp granularity, rather than independently
  advancing only one CUDA thread. Use `cuda thread`, `cuda warp`, and
  `cuda lane` to inspect other execution contexts.
- Warp divergence is visible in the output of `info cuda warps` and
  `info cuda lanes`.
- Device code must be compiled with `-G` (`nvcc`) or `-gpu=debug` (`nvc` and
  `nvc++`) for GPU debugging symbols. Without it, CUDA-GDB cannot reliably map
  device execution to source lines.
- On multi-GPU systems, use `cuda device N` to select the GPU under
  investigation.
- The set of available `info cuda` and `cuda` commands can depend on the GPU,
  driver, and CUDA-GDB version.

## 7. Limitation: printing `std::vector<>` in CUDA-GDB

CUDA-GDB supports printing `std::vector<>` using libstdc++ pretty-printers:

```text
(cuda-gdb) print vec
$1 = std::vector of length 4, capacity 4 = {0, 1, 2, 3}
```

However, support for evaluating C++ vector member functions and overloaded
operators may be limited:

```text
(cuda-gdb) print vec.size()
Cannot evaluate function -- may be inlined

(cuda-gdb) print vec.data()
Cannot evaluate function -- may be inlined

(cuda-gdb) print vec[0]
Could not find operator[].
```

Workarounds:

```text
# Print the entire vector
(cuda-gdb) print vec

# Print vector size
(cuda-gdb) print (vec._M_impl._M_finish - vec._M_impl._M_start)

# Print the first element
(cuda-gdb) print *vec._M_impl._M_start

# Print all elements (4 elements)
(cuda-gdb) print *(vec._M_impl._M_start)@4
```

Conclusion: `std::vector<>` can be displayed using pretty-printers, but
evaluating its member functions (`size()`, `data()`) and overloaded operators
(`operator[]`) may not work in CUDA-GDB.
